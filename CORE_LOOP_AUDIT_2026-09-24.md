# Theme Park Shark core loop audit

**Date:** September 24, 2026  
**Scope:** Gameplay and release readiness. Preserve the existing visual design.  
**Owner's intended loop:** Home GPS set hunt -> Energy, XP, Tickets -> in-park ride coin attempt -> ride-specific Parts -> Energy + Parts upgrade the coin -> park completion, shark identity, stamps, and leaderboards. Queue time adds Parts and optional activities.

## Verdict

**Keep the concept. Finish and prove the chain.** A location-based coin collection game tied to real rides is a distinctive premise. The collectible has a real-world story: "I was there." Ride-specific Parts and shared Energy give a sound reason to play both at home and at the park. Since the initial audit, local app and backend changes have connected authoritative ride attempts, first-coin collection, Parts, and coin upgrades. This is still unproven as a live park experience: backend migrations and deployment, signed-in device play, physical GPS and queue behavior, and guest enjoyment remain release gates. More side games will only help if they strengthen that main payoff.

### Local implementation update — a short remote Park Project challenge

Fans who cannot take a walk or visit a park today can now answer an authored story question for the Park Project they follow. The backend chooses a question by the park's local day, validates the answer without sending the answer key to the app, and records one completion per user/project/day. A correct answer can add one remote project point under the existing daily and shared caps. A wrong answer can be retried without consuming the day. The response distinguishes a correct answer from points actually awarded, and the app shows this inside the home Park Project panel. This can unlock the same personal clue, crew clue, event stamp, and chapter vote as other verified project participation; it cannot award a ride coin, Ride Part, Ticket, or XP. The authored pilot and its two sequel paths each have a small challenge deck. The launch command validates that deck before creating a project; the feature remains under the existing off-by-default Park Projects flag.

The player API suite passes **69 tests with 806 assertions**, including wrong answers, daily replay, next-day rotation, and the off switch. An Expo iOS export passes and `git diff --check` passes. The app-wide typecheck still reports 43 existing errors outside the changed project files. This is a small, repeatable remote action, not a complete at-home game. The three-question decks repeat during a week, and no fan enjoyment, real-time update, or installed-device test has been observed. More authored content and a real remote-fan playtest are required before claiming the home loop feels fresh. The migration and code are local, not deployed.

Replaying a resolved loss cannot refund again. The app offers an immediate fresh attempt from that result; a later loss spends its Ticket normally. This is meant to prevent a new park guest from being stranded after one random mini-game loss, while keeping the challenge and Ticket economy intact.

The flag defaults **off**. A new local migration adds the user marker and attempt field; it has not been applied to production. Six backend suites pass **41 tests with 486 assertions**, including first-loss refund, replay, second loss, and refusal after a collected coin. The app still has 127 wider TypeScript errors but no reported errors in the changed attempt UI, and the iOS bundle exports. A device test must check the retry transition, weak connection, and whether real new players understand the rule before enabling the flag. This does not validate mini-game outcomes against tampering; that remains a separate economy and leaderboard gate.

### Twenty-first local implementation update: game-result plausibility pilot

The MiniGameSelector now passes its result data through the ticketed attempt flow instead of discarding it. It no longer invents coin or XP amounts for a ticketed game callback; only the server's resolved attempt can award those. ## Is the game idea strong enough?

**Yes, with three mechanical adjustments.** These preserve the visual design and the owner's goals.

1. **Make the first coin a park-day win.** A guest who physically reaches a ride should be able to earn its base coin during that visit. Tickets and mini-games can make the attempt engaging, but an empty ticket wallet, a level lock, or a lost random challenge should not make the trip's defining souvenir impossible. Put stronger gates on repeats, mastery tiers, rare variants, and optional bosses. This is a recommendation to test, not a claim that every guest prefers easy rewards.
2. **Give the first upgrade quickly and make later mastery deep.** The current level-2 cost is 5 Parts + 10 Energy; the five-level backend schedule totals **125 Parts and 185 Energy** to max one coin (`PlayerCoinLevel.php:25-41`). At the proposed passive rate of one Part per ten queue minutes, 125 Parts would mean **20 hours 50 minutes** at that single ride if queueing were the only source. Tasks and bonus games should reduce that, but the balance must be simulated across typical trip lengths before launch. A player should see the first real upgrade and its effect on the same park day.
3. **Treat sets as preparation with a fair finish path.** Forty equally likely variants drawn with replacement would require about **171 pickups on average** to complete once, or **5.7 per day in a 30-day month**. Actual rarity weights could make this longer. This is illustrative math, not the current spawn distribution. Add duplicate conversion, a wildcard or deterministic last-item path, and an alternate route for weather-only finds. Keep rotating sets, but verify a casual player can finish a season without changing local weather or making daily chores the main attraction.

The better version of the idea is **the same park coin game with a guaranteed meaningful visit record, a real coin upgrade economy, and a clear path from home preparation to the next ride goal**. A generic daily collector, PvP wager economy, or separate idle park game would add complexity before this proof exists. Optional PvP belongs after Parts, fairness, abuse controls, and queue verification work reliably; wagering scarce ride-specific Parts is especially likely to punish casual players.

## Product decision — protect rare park visits, reward repeat visits

Dustin's direction: home and park guests should both make meaningful progress; frequent local visitors may advance much further. Queue play should support solo, one-phone family, and nearby-player experiences, but nearby participation can never be required to have fun. A small comparison of relevant, highly rated mobile games informed this decision: Pikmin Bloom uses local collecting plus shared challenges that work across distance (US App Store 4.8/5, 67K ratings); Brawl Stars supports solo or friend play and rotating short modes (4.7/5, 3.1M ratings); Pokémon GO keeps collecting as its broad entry loop (4.0/5, 654K ratings). Supercell says Brawl Stars' old mastery track became a niche farm for highly active players and moved progression into more accessible paths; only 11.8% had earned a Brawler Title. Sources: https://apps.apple.com/us/app/pikmin-bloom/id1556357398 ; https://apps.apple.com/us/app/brawl-stars/id1229016807 ; https://apps.apple.com/us/app/pok%C3%A9mon-go/id1094591345 ; https://supercell.com/en/games/brawlstars/blog/news/rip-masteries ; https://support.supercell.com/brawl-stars/en/articles/game-modes-12.html . These are design references, not evidence TPS is as fun or as well rated.

**Rule:** a physically visited, available ride's *base coin* should be attainable on the visit without an XP level lock. XP, ride-specific Parts, and repeat visits should expand mastery, editions, harder challenges, cosmetics, and leaderboard depth. Tickets provide a light attempt rhythm rather than a rare-trip wall. The local backend already tops a verified guest up to two Tickets once per park-local day, charges one per ride challenge, returns the first lost attempt's Ticket once per unowned ride per day, and grants a next-ride Ticket after a first base-coin win. Those rules need signed-in field verification before claiming the whole first-day route works. The bounded zero-Ticket rescue described below extends this path when a guest runs out; it remains gated pending a park pilot. Do not silently grant unlimited attempts or mint Tickets client-side.

Queue design follows the same principle: each wait should have an authored solo activity and a one-phone group activity immediately available; community actions can change a shared route or unlock an extra puzzle when enough people participate. If the park is quiet or no one opts in, the personal route remains playable. The upcoming pilot should compare solo, family, and spontaneous-nearby play in real 15–45 minute waits.

## Owner decision — first ride access and solo-first queue play

Dustin confirmed that an active local guest should be able to advance much faster than a fan at home, while both can make real progress. He also wants queue play with nearby guests when possible, without requiring another player to be present. The design decision is to let a verified visitor earn an unowned **base** ride coin at that ride without an XP gate. Tickets remain the normal challenge currency; when empty, a narrowly limited rescue attempt should protect a rare park visit. Put stronger progression gates on coin upgrades, editions, rare challenges, and bosses. Keep the first-coin challenge interactive and server-verified. The local backend already has no XP check for a base attempt and implements an off-by-default one-per-park-day Shark Rescue Pass with one same-ride retry. This remains a pilot rule, not a shipped promise; observe whether two tries feel fair and whether guests understand the Ticket loop.

The queue design rule is that every chapter must be complete and enjoyable solo, then gain an optional cooperative or competitive layer through one-phone handoff or nearby guests. A missing opponent must never block a chapter, its reward, or its story ending. This is informed by the accessible location reward and cooldown in [Pokémon GO PokéStops](https://niantic.helpshift.com/hc/en/6-pokemon-go/faq/117-visiting-pokestops-and-gyms/), group challenges that can start with a single player in [Pikmin Bloom](https://niantic.helpshift.com/hc/en/23-pikmin-bloom/faq/3404-weekly-challenges/), and collection plus rotating social events in [MONOPOLY GO!](https://www.scopely.com/en/news/its-time-to-take-that-chance-monopoly-go-is-here).
